# PRD — School-Management (نظام إدارة مدرسية)

## Part 1 — Business Overview

**نظرة عامة:**
نظام إدارة مدرسية شامل (ERP) يهدف لمركزة إدارة العمليات المدرسية اليومية في لوحة تحكم واحدة — من إدارة الطلاب والمدرسين والموظفين، وحتى الجدول الدراسي والامتحانات.

**المستخدمين (Actors):**

* **Admin / المدير**: صلاحية كاملة على النظام
* **مشرفين معتمدين**: صلاحيات محددة حسب الدور (يُدار عبر شاشة "الصلاحيات")

**نطاق التنفيذ (Scope):** 8 موديولات مختارة من أصل 12 موديول في التصميم الأصلي، بإجمالي 38 شاشة:

|#|الموديول|عدد الشاشات|
|-|-|-|
|1|تسجيل الدخول|8|
|2|وحدة التحكم (Dashboard)|6|
|3|الطلاب|8|
|4|المدرسين|6|
|5|الموظفين والصلاحيات|7|
|6|الجدول الدراسي|1|
|7|الامتحانات والمراجعات|1|
|8|الإعدادات|1|

الموديولات المستبعدة من النطاق (موثقة في التصميم، غير منفذة في هذا الإصدار): المالية والحسابات، المواد الدراسية، رفع النتائج، إعداد هيكل المدرسة.

## Part 2 — Product Detail (لكل Feature)

### Feature 1: تسجيل الدخول (Authentication)

**User Story:**
بصفتي مديرًا أو مشرفًا معتمدًا، أريد تسجيل الدخول بـ ID وكلمة سر عشان أدخل على لوحة التحكم الخاصة بي، مع إمكانية استرجاع كلمة السر لو نسيتها.

**الشاشات المرتبطة:**

1. **تسجيل الدخول** — فورم رئيسي (حقل ID + حقل كلمة السر + رابط "نسيت كلمة السر؟") **+ Demo credentials ظاهرة بوضوح فوق الفورم + زرار "دخول تجريبي سريع" (تفاصيل كاملة في `workflow.md` قسم 3.1)**
2. **إدخال رقم الهاتف** — خطوة 1 من استرجاع كلمة السر
3. **إدخال كود التحقق** — خطوة 2: كود تحقق مُرسل على الهاتف
4. **إنشاء كلمة سر جديدة** — خطوة 3: تعيين كلمة سر جديدة
5. **تسجيل الدخول لأول مرة** — تدفق مختلف لأول استخدام
6. **اضافة بيانات المدرسة** — Onboarding: بيانات المدرسة عند أول تسجيل دخول
7. **عدم الاتصال بالانترنت** — Empty/Error state
8. **جاري التحميل** — Loading state

**Flow:**

```
تسجيل دخول عادي:
شاشة الدخول → إدخال ID + Password → نجاح → Dashboard
                                    → فشل → رسالة خطأ (نفس الشاشة)

أول مرة:
شاشة الدخول → نجاح → "تسجيل الدخول لأول مرة" → "إضافة بيانات المدرسة" → Dashboard

نسيت كلمة السر:
"نسيت كلمة السر؟" → إدخال رقم الهاتف → إدخال كود التحقق → إنشاء كلمة سر جديدة → شاشة الدخول
```

**Edge Cases:**

* ID أو كلمة سر خاطئة → رسالة خطأ واضحة تحت الحقل، بدون تحديد أي حقل بالتحديد كان الخطأ (Security best practice)
* عدم اتصال بالإنترنت أثناء أي خطوة → عرض شاشة "عدم الاتصال بالانترنت" مع خيار إعادة المحاولة
* كود التحقق منتهي الصلاحية → رسالة خطأ + خيار "إعادة إرسال الكود"
* الحساب مقفول بعد محاولات فاشلة متكررة → (يحتاج قرار: هل ننفذ Rate limiting في هذا الإصدار أم نؤجله؟)

**شكل البيانات المتوقع (تمهيدًا لـ TypeScript Types):**

```
LoginRequest: { id: string, password: string }
LoginResponse: { token: string, user: { id, name, role, schoolId } }
ForgotPasswordRequest: { phone: string }
VerifyCodeRequest: { phone: string, code: string }
ResetPasswordRequest: { phone: string, code: string, newPassword: string }
```

### Feature 2: وحدة التحكم (Dashboard)

**User Story:**
بصفتي مديرًا، أريد رؤية نظرة عامة سريعة على حالة المدرسة (عدد الطلاب، الأرباح، طلبات الاجتماعات، نشاط المستخدمين) في شاشة واحدة.

**الشاشات المرتبطة:**

1. **وحدة التحكم** — الشاشة الرئيسية (تفصيل كامل بالأسفل)
2. **إرسال إشعار لجميع مستخدمي التطبيق**
3. **اضافة الطالب** (Shortcut من الداشبورد لنفس فورم الإضافة في موديول الطلاب)
4. **إشعارات** — صفحة/Panel الإشعارات
5. **إنشاء كلمة سر للتطبيقات**

**مكونات الشاشة الرئيسية:**

|القسم|الوصف|
|-|-|
|**KPI Cards (×3)**|طلبات الاجتماعات (48) / جميع الطلاب (3,764) / الأرباح (60,000 + نسبة تغيّر)|
|**Chart النشاط الأسبوعي**|Bar chart مقسم حسب اليوم والجنس (طالب/طالبة) — Recharts|
|**كروت الأداء (×2)**|أداء الموظفين هذا الشهر / تفاعل المدرسين على التطبيق — بخلفية صورة + نسبة مئوية|
|**Search bar عام**|بحث عن طالب/مدرس/موظف من أي مكان في الداشبورد|
|**أزرار سريعة**|إضافة/استيراد بيانات، إنشاء كلمة سر للتطبيقات، إضافة طالب، إرسال إشعار لكل المستخدمين|

**Edge Cases:**

* مفيش بيانات كفاية لعرض الـ Chart (مدرسة جديدة، أول أسبوع) → Empty state بدل Chart فاضي
* فشل تحميل بيانات الـ KPIs → Skeleton loading ثم رسالة خطأ لو فشل الطلب

### Feature 3: الطلاب (Students Management)

**User Story:**
بصفتي مديرًا، أريد إدارة بيانات كل الطلاب (عرض، إضافة، تعديل)، ومتابعة حالة "القيد" (Enrollment) الإدارية والمالية لكل طالب بشكل منفصل عن بياناته الشخصية.

**الشاشات المرتبطة:** قائمة الطلاب، جميع بيانات الطالب وإدارتها، تعديل بيانات الطالب، إضافة الطالب، إرسال إشعار للطالب وولي الأمر، قيد الطالب، تعديل قيد الطالب، اجراء القيد

**ملاحظة معمارية:** الموديول ده مقسّم لكيانين منفصلين منطقيًا:

* **بيانات الطالب (Student Profile)** — بيانات شخصية/صحية/ولي أمر
* **القيد (Enrollment)** — سجل إداري/مالي/أكاديمي منفصل، مرتبط بالطالب لكنه Entity قائم بذاته

#### 3.1 قائمة الطلاب (List)

**الأعمدة:** الاسم (+ Checkbox تحديد)، ID الطالب، الصف الدراسي، الفصل، البريد الإلكتروني، الجنس، فعل (رؤية / تعديل)، حالة القيد (نشط / خطأ)

**عناصر التحكم:** Search bar، Filter بعدد الصفوف (100/صفحة)، Filter بـ"المرحلة" (Dropdown)، أزرار (إضافة/استيراد بيانات، إضافة طالب)، Pagination

**Edge Cases:**

* قائمة فاضية (مفيش طلاب) → Empty state مع CTA "إضافة أول طالب"
* فشل تحميل القائمة → رسالة خطأ + زرار إعادة المحاولة
* حالة القيد "خطأ" → لازم توضيح إيه المشكلة عند الـ Hover/Click (تفاصيل الخطأ)

#### 3.2 إضافة/تعديل الطالب (فورم من 3 أقسام)

**Section 1 — Student Info:**
الجنس، تاريخ الميلاد، الاسم، رقم الطالب (Student ID)، الرقم القومي، البريد الإلكتروني، العنوان، الديانة، الجنسية، المرحلة التعليمية

**Section 2 — Guardian Info (بيانات ولي الأمر — أب وأم منفصلين):**

* الأب: الرقم القومي، البريد الإلكتروني، الاسم، الجنسية، رقم الهاتف
* الأم: الرقم القومي، البريد الإلكتروني، الاسم، الجنسية، العنوان، رقم الهاتف

**Section 3 — Health Info:**
مرض مزمن (Chronic Illness)، الطول، الوزن، الحساسية (Allergy)، فصيلة الدم، أدوية يومية، رقم الطبيب، اسم الطبيب، المستشفى

**Edge Cases:**

* حقول Health Info كلها اختيارية (مش كل طالب عنده حالة صحية خاصة)
* تكرار الرقم القومي/البريد الإلكتروني لطالب موجود بالفعل → Validation error واضح
* حفظ جزئي (Draft) لو الفورم طويل والمستخدم مقاطَع؟ (قرار مفتوح: نأجله للإصدارات القادمة)

#### 3.3 قيد الطالب (Enrollment Record) — Workflow منفصل

**الأقسام:**

* **سجل القيد (Registration History)** — Table بتاريخ حالات القيد السابقة
* **ملخص القيد (Registration Summary)** — بيانات ملخصة عن حالة القيد الحالية
* **القرارات الإدارية (Administrative Decisions)** — مثال ظاهر في التصميم: "الطالب محوّل من مدرسة النور الأهلية - يتطلب متابعة" (يوضح إن فيه قرارات/ملاحظات إدارية نصية لكل طالب)، بالإضافة لنسب خصم (Discount Rate)
* **المسار الأكاديمي (Academic Path)** — قائمة بمراحل الطالب الدراسية
* **الملخص المالي (Financial Summary)** — بيانات مالية مرتبطة بالقيد (رسوم، مدفوعات)

**Edge Cases:**

* طالب جديد بدون سجل قيد سابق → Empty state في RegistrationHistory
* قرار إداري بدون نص (مفيش ملاحظات) → إخفاء القسم أو عرض "لا توجد ملاحظات"

**شكل البيانات المتوقع:**

```
Student: {
  id, name, gender, birthDate, nationalId, email, address, religion,
  nationality, educationLevel,
  guardian: {
    father: { nationalId, email, name, nationality, phone },
    mother: { nationalId, email, name, nationality, address, phone }
  },
  health: { chronicIllness?, height?, weight?, allergy?, bloodType?, dailyMedication?, doctorName?, doctorPhone?, hospital? } | null,
  enrollmentStatus: 'active' | 'error'
}

Enrollment: {
  studentId: string,
  history: { date, status, type, notes }\\\\\\\[],
  administrativeDecisions: { note: string, discountRate?: number }\\\\\\\[],
  academicPath: { stage: string, year: string }\\\\\\\[],
  financialSummary: { totalFees: number, paid: number, remaining: number, status: string }
}
```

### Feature 4: المدرسين (Teachers Management)

**User Story:**
بصفتي مديرًا، أريد إدارة بيانات المدرسين الشخصية والوظيفية والعلمية بشكل منظم، عشان أقدر أتابع كل مدرس (المواد اللي بيدرّسها، راتبه، مؤهلاته).

**الشاشات المرتبطة:** قائمة المدرسين، بيانات المدرس، تعديل بيانات المدرس، إضافة مدرس، إرسال إشعار (×2)

#### 4.1 قائمة المدرسين (List)

نفس باترون "قائمة الطلاب" (Table + Search + Filters + Pagination)، بس بأعمدة خاصة بالمدرسين.

#### 4.2 إضافة/تعديل المدرس (فورم من 3 أقسام)

**Section 1 — البيانات الشخصية:**
تاريخ الميلاد، الجنس، اسم المعلم، الرقم التعريفي (ID)، رقم الهوية، محل الإقامة، فصيلة الدم، الديانة، الجنسية، كلمة السر، البريد الإلكتروني، رقم الهاتف

**Section 2 — البيانات الوظيفية:**
الأجازات الشهرية، الدرجة المعين عليها، تاريخ التعيين، الصفوف المسؤول عنها، الساعات الإضافية، اليوم الإضافي، المواد المسؤول عنها، الراتب، عدد ساعات العمل، تاريخ انتهاء التعيين، الخصم

**Section 3 — البيانات العلمية:**
اللغات الإضافية، اسم الجامعة، المؤهل، عدد سنوات الخبرة، شهادات، التقدير التراكمي، الشهادات المدرجة (رفع PDF)، إرفاق ملف (رفع PDF)

**Edge Cases:**

* رفع ملفات PDF (الشهادات) → حد أقصى لحجم الملف + رسالة خطأ لو الصيغة غلط
* "الصفوف المسؤول عنها" و"المواد المسؤول عنها" مرتبطين منطقيًا بموديول "الجدول الدراسي" لاحقًا — لازم الـ Type يكون متسق بين الموديولين
* تاريخ انتهاء التعيين قبل تاريخ التعيين → Validation error

**شكل البيانات المتوقع:**

  },

### Feature 5: الموظفين والصلاحيات (Employees \& Permissions/RBAC)

**User Story:**
بصفتي مديرًا، أريد إدارة بيانات الموظفين الإداريين (غير المدرسين)، والأهم: التحكم الدقيق فيما يقدر كل موظف يشوفه أو يعدله في النظام (Role-Based Access Control).

**الشاشات المرتبطة:** قائمة الموظفين، بيانات الموظف، تعديل بيانات الموظف، إضافة موظف، **الصلاحيات**، إرسال إشعار (×2)

#### 5.1 قائمة الموظفين + إضافة/تعديل موظف

نفس باترون قائمة المدرسين بالضبط. فورم الإضافة/التعديل مطابق لفورم المدرس (3 أقسام: شخصية/وظيفية/علمية)، بفرق واحد: حقل **"نوع الوظيفة"** بدل "الدرجة المعين عليها" في القسم الوظيفي (الموظف مش بالضرورة مدرس).

#### 5.2 شاشة "الصلاحيات" (Permissions Matrix) — الأهم في الموديول ده

**الوصف:** شاشة مخصصة لكل موظف على حدة، بتعرض صورته واسمه ومسماه الوظيفي، وجدول صلاحيات بعمودين (**تعديل** / **رؤية**) قدام كل فئة بيانات في النظام:

|الفئة|Checkbox رؤية|Checkbox تعديل|
|-|-|-|
|البيانات الأساسية للطالب|✓|✓|
|البيانات الأكاديمية|✓|✓|
|التسجيل والقيد|✓|✓|
|البيانات الشخصية للمعلم|✓|✓|
|البيانات الشخصية للموظف|✓|✓|
|الفصول الدراسية|✓|✓|
|مواعيد الاختبارات والنتائج|✓|✓|
|**تحديد الكل**|✓ (Select All)|✓ (Select All)|

أزرار: **حفظ** (Primary) / **إلغاء** (Outline)

**Edge Cases:**

* تفعيل "تعديل" بدون "رؤية" لنفس الفئة → منطقيًا غير مسموح (لازم تقدر تشوف عشان تعدل) — الفورم لازم يفرض إن اختيار "تعديل" يفعّل "رؤية" تلقائيًا
* المدير نفسه (Admin) → صلاحياته Full access ثابتة، مش معروضة في الشاشة دي (الشاشة للموظفين المُنشأين تحته بس)
* محاولة موظف الوصول لصفحة مالوش صلاحية عليها → Redirect لصفحة "غير مصرح" (403-style page)

**شكل البيانات المتوقع:**

```
Employee: {
  id, name, gender, birthDate, nationalId, address, bloodType, religion, nationality,
  email, phone, password, jobType,
  employment: { monthlyLeaves, appointmentDate, endDate, overtimeHours, extraDay, salary, workHours, discount },
  academic: { additionalLanguages, university, qualification, yearsOfExperience, certificates, gpa, certificateFiles, attachedFile }
}

Permission: {
  employeeId: string,
  categories: {
    category: 'student\\\\\\\_basic\\\\\\\_data' | 'academic\\\\\\\_data' | 'enrollment' | 'teacher\\\\\\\_personal\\\\\\\_data' |
              'employee\\\\\\\_personal\\\\\\\_data' | 'classes' | 'exams\\\\\\\_results',
    canView: boolean,
    canEdit: boolean
  }\\\\\\\[]
}
```

### Feature 6: الجدول الدراسي (Schedule Builder)

**User Story:**
بصفتي مديرًا، أريد بناء الجدول الدراسي الأسبوعي بصريًا — أختار مادة ومدرس وفصل وحصة زمنية وأضيفها للجدول، مع إمكانية التنقل بين الأيام عبر تقويم مصغّر ومتابعة حصص اليوم الحالي بسرعة.

**الشاشات المرتبطة:** شاشة واحدة (Single view مركّبة من عدة أجزاء تفاعلية)

**مكونات الشاشة:**

|القسم|الوصف|
|-|-|
|**Mini Calendar**|تقويم مصغّر (شهر/سنة + أسهم تنقل) لاختيار اليوم المعروض|
|**فلاتر متعددة**|تحديد الصفوف، تحديد المراحل، اختيار/كتابة المادة، الفصل، المدرس، الحصة (كلهم Dropdowns قابلة للكتابة أيضًا — Combobox)|
|**"اضف حصة"**|إجراء إضافة حصة جديدة للجدول بناءً على الفلاتر المختارة|
|**حصص اليوم**|قائمة جانبية بكل حصص اليوم الحالي (اسم المادة + رقم الحصة + التوقيت)|
|**Table/Grid الجدول الرئيسي**|الجدول الأسبوعي الفعلي (900×667px) — أيام × حصص|
|**Search bar عام**|بحث سريع|
|**Control buttons**|غالبًا تبديل بين طرق العرض (أسبوعي/شهري) — يحتاج تأكيد بصري إضافي وقت التنفيذ|

**Edge Cases:**

* تعارض حصتين (نفس المدرس/الفصل في نفس التوقيت) → لازم Validation يمنع الحفظ ويوضح التعارض
* يوم بدون حصص → Empty state في قائمة "حصص اليوم"
* حذف حصة من الجدول → Confirmation dialog قبل الحذف

**شكل البيانات المتوقع:**

```
ScheduleSlot: {
  id, subjectId, subjectName, classId, className,
  teacherId, teacherName, period: number,

Subject: { id, name }
Period: { id, order, startTime, endTime }
```

### Feature 7: الامتحانات والمراجعات (Exams \& Review Schedule)

**User Story:**
بصفتي مديرًا، أريد جدولة مواعيد الامتحانات والمراجعات بنفس منطق جدولة الحصص الدراسية، عشان أوزّع الامتحانات على أيام وفترات محددة بدون تعارض.

**الشاشات المرتبطة:** شاشة واحدة

**ملاحظة معمارية مهمة:** الشاشة دي بتستخدم نفس الـ Components بالظبط اللي في موديول "الجدول الدراسي" (نفس الـ Sidebar، نفس Table Component "Table اضافة جدول الحصص"، نفس Search bar، نفس أزرار التحكم) — يعني **في الكود، الاتنين المفروض يشاركوا نفس الـ React Component** (Generic `ScheduleGrid`) بفرق بس في نوع البيانات (حصص دراسية مقابل مواعيد امتحانات) والـ Props اللي بتتبعت له.

**Edge Cases:** نفس Edge cases موديول الجدول الدراسي (تعارض مواعيد، إلخ) + احتمال تعارض إضافي: امتحان في نفس وقت حصة دراسية عادية لنفس الفصل.

**شكل البيانات المتوقع:**

```
ExamSlot: {
  id, subjectId, subjectName, classId, className,
  type: 'exam' | 'review',
  date: string, startTime: string, endTime: string
}
```

### Feature 8: الإعدادات (Settings)

**User Story:**
بصفتي مستخدمًا (مدير/موظف)، أريد إدارة بياناتي الشخصية، أمان حسابي، ولغة الواجهة من مكان واحد.

**الشاشات المرتبطة:** شاشة واحدة، مقسّمة بـ Tabs

**Tabs:**

1. **الملف الشخصي (Profile)** — التاب الوحيد ضمن نطاق التنفيذ (تفصيل كامل أدناه)

**ملاحظة Scope:** التصميم الأصلي فيه تابين إضافيين ("الأداء" و"الأمان") — **مُستبعدين بالكامل من نطاق هذا الإصدار**. هيظهروا في الـ UI كتابات غير قابلة للنقر (Disabled) أو يتم إخفاؤهم، حسب القرار وقت التنفيذ.

**Tab الملف الشخصي — الحقول:**

* عمود 1: اسم المستخدم، البريد الإلكتروني، تاريخ الميلاد، رقم الهاتف
* عمود 2: الاسم المعروض، الرقم التعريفي (ID)، كلمة السر، العنوان، البلد
* صورة شخصية (قابلة للتعديل — أيقونة Edit فوق الصورة)
* **تغيير اللغة** — Dropdown منفصل (يشير لدعم تعدد اللغات في الواجهة — قرار مهم: هل ننفذ i18n فعليًا في هذا الإصدار أم نكتفي بالـ UI بدون وظيفة فعلية؟)

أزرار: **حفظ** (Primary) / **إلغاء** (Outline)

**Edge Cases:**

* تغيير البريد الإلكتروني → يحتاج تأكيد (Verification) قبل التفعيل
* تغيير كلمة السر → يتطلب إدخال كلمة السر الحالية أولاً (Security best practice)

**شكل البيانات المتوقع:**

```
UserSettings: {
  username, email, birthDate, phone,
  displayName, id, address, country,
  profileImage?: string,
  language: 'ar' | 'en'
}
```
